# Мониторинг ресурсов ТПУ — архитектурная основа v2.1

**Источник требований:** исходное ТЗ «Мониторинг ресурсов ТПУ». Это готовая к совместной разработке **основа БД, схем обмена и транзакционного слоя**, а не полностью реализованное приложение мониторинга. API, сетевые проверки, планировщик и Mock API развиваются отдельными задачами по тому же ТЗ.

## Что зафиксировали

- Технологии из ТЗ: SQLite, Python 3.12+, FastAPI, Pydantic, httpx, asyncio, pytest, Docker Compose. В этом пакете уже используются SQLite, SQLAlchemy 2, Pydantic v2 и pytest.
- **Один `resource_id` означает одну проверяемую службу и один тип проверки** (HTTP/HTTPS или TCP). ICMP оставлен необязательным будущим улучшением.
- Статусы: новый ресурс `UNKNOWN`, после двух успешных проверок `UP`, после трёх неуспешных `DOWN`. Пороги задаются в конфигурации.
- `STATUS_CHANGED` при первом подтверждённом состоянии и смене итогового статуса; `HEARTBEAT` через настраиваемые 300 секунд независимо от смены статуса.
- Отправка по HTTP POST во внешний сервис, адрес и токен — только из окружения. Mock API должен принимать дубли по одному `event_id` идемпотентно.
- Реальных внутренних проверок ТПУ **не выполняем** до выдачи согласованных доступов.
- **Не** заменяем SQLite на PostgreSQL и **не** расширяем `resource_id` до агрегата нескольких служб.

## 1. Нормализованная база SQLite

| Таблица | Ключи / функциональное назначение | Отношения |
|---|---|---|
| `resources` | `id` PK; неизменный идентификатор службы, название, признак активности, даты | `1:N` к версиям конфигурации |
| `resource_config_versions` | `id` PK; `resource_id` FK, `version_number` UNIQUE в рамках ресурса; цель, метод проверки, порт, таймауты, пороги, интервалы, срок действия | `1:N` к истории проверок, `1:N` к HTTP-диапазонам; одна активная версия на ресурс |
| `http_expected_ranges` | PK `(config_version_id,code_start,code_end)`; HTTP-коды и диапазоны вместо строки со списком | `N:1` к версии конфигурации |
| `resource_states` | `resource_id` PK, FK; `config_version_id` FK; текущий статус, счётчики, даты, номер ревизии | `1:1` к ресурсу, ссылка на его конфигурацию |
| `check_results` | `id` PK; `resource_id` и `config_version_id` FK; факты проверки, отклик и полученный статус | `N:1` к версии и ресурсу |
| `status_transitions` | `id` PK; `check_result_id` UNIQUE; исходный/новый статусы, момент перехода | `1:1` к проверке, только когда итоговый статус изменился |
| `outbox_events` | `event_id` UUID PK; snapshot JSON, тип, статусы доставки, попытки, lease | `N:1` к ресурсу; необязательная `1:1` к `status_transitions` |
| `delivery_attempts` | `id` PK; `(event_id, attempt_number)` UNIQUE; HTTP-код, причина, исход | `N:1` к `outbox_events` |

Текущая версия содержит **8 предметных таблиц**, а Alembic ведёт дополнительно служебную `alembic_version`.

### Почему такая декомпозиция и 3НФ

**Пример основных функциональных зависимостей:**

- `resources.id -> {name, active, created_at, updated_at}`.
- `resource_config_versions.id -> {resource_id, version_number, target, check_type, ...}` и `(resource_id, version_number)` — альтернативный ключ.
- `resource_states.resource_id -> {config_version_id, current_status, ok_count, fail_count, ...}`.
- `check_results.id -> {resource_id, config_version_id, checked_at, success, ...}`.
- `status_transitions.id -> {check_result_id, previous_status, new_status, changed_at}`; `check_result_id` уникален.
- `outbox_events.event_id -> {resource_id, event_type, payload_json, delivery_status, ...}`.
- `delivery_attempts.id -> {event_id, attempt_number, outcome, ...}`; `(event_id, attempt_number)` — альтернативный ключ.

Операционные сведения о статусе не помещены в `resources`; история проверки не перезаписывается; последовательные конфигурации имеют отдельные ключи и периоды действия. В каждой таблице неключевые атрибуты зависят от выбранных ключей сущности, а не от других неключевых атрибутов. Подробное доказательство 3НФ перед защитой требует отдельной фиксации **полного набора предполагаемых функциональных зависимостей** и проверки по всем кандидатным ключам. База отражает выбранную модель предметной области, а не автоматически доказывает все нормальные формы самим фактом разделения таблиц.

**Обоснованная избыточность:** `resource_states` — транзакционно поддерживаемая проекция текущего состояния из потока проверок, чтобы быстро обслуживать GET API. `outbox_events.payload_json` — *неизменяемый снимок* для at-least-once доставки; его содержимое и часть индексируемых атрибутов события намеренно повторяют информацию, чтобы повторная отправка не зависела от изменившегося имени/состояния ресурса. `attempts` в outbox — материализованный счётчик, поддерживаемый вместе с историей `delivery_attempts` в одной транзакции. Эти компромиссы нужно честно объяснять преподавателю, а не выдавать их за отсутствие дублирования.

**Проверки БД:** `FK`, `UNIQUE`, `CHECK`, составные FK принадлежности версии ресурсу, частичный индекс «одна активная конфигурация», триггер неизменяемого события, составные индексы по истории и очереди.

### Идемпотентность загрузки конфигурации

Повторный импорт того же ресурса без изменения параметров **не создаёт новую версию и не сбрасывает статус** — это важно при перезапуске. Изменение интервалов/порогов/таймаутов или признака активности создаёт новую версию, сбрасывает последовательные счётчики, но сохраняет последний подтверждённый статус, пока новая проверка не даст достаточно доказательств. Изменение самого `target`, `check_type`, `port` или HTTP-критерия — изменение *идентичности проверяемой службы*; в утверждённом контракте требуется новый `resource_id`. Это консервативное правило исключает бездоказательные статусы `UNKNOWN` и неподтверждённые `STATUS_CHANGED` при административной правке.

## 2. Классы

`shared/schemas.py` содержит `ResourceConfig`, `ExpectedHttpRange`, `ResourceRead`, `CheckSnapshot`, `CheckResultIn`, `CheckResultRead`, `ResourceStatusRead`, `StatusEventContext`, `StatusEventPayload`, `OutboxEventRead`, а также Enum `CheckType`, `ResourceStatus`, `EventType`, `DeliveryStatus`. Поля соответствуют внешнему формату из ТЗ: `event_id`, `resource_id`, `resource_name`, `status`, `check_type`, `checked_at`, `response_time_ms`, `error`, `event_type`.

Важное различие: это **Pydantic DTO**, а не SQLAlchemy ORM-сущности. Доступ к таблицам в данной версии сознательно реализован параметризованным SQL через SQLAlchemy Core, с прямым контролем используемых ограничений. Добавление ORM допустимо, но не является условием 3НФ.

## 3. Инварианты, конкуренция и транзакции

- В каждой операции `apply_check_result()` **одной транзакцией** фиксируются `check_results`, `resource_states`, `status_transitions` и `outbox_events` (если статус изменился).
- `record_status_change(conn, previous_status, context, check_result_id)` **не отправляет HTTP и не вызывает commit**; транзакцией владеет вызывающий обработчик Никиты.
- `BEGIN IMMEDIATE` берёт блокировку писателя **до чтения текущих счётчиков**, поэтому два параллельных процесса не могут потерять инкремент. Это сериализует SQLite-писателей, и для данного масштаба допустимо. Соединения включают `PRAGMA foreign_keys=ON` и `busy_timeout`.
- **Снимок версии до сетевого запроса:** `get_active_check_snapshot()` читает `config_version_id` и все параметры HTTP/TCP до начала сетевого I/O. `CheckResultIn.config_version_id` обязателен; он переносится только из этого снимка.
- **Защита от устаревшей конфигурации:** `apply_check_result()` внутри `BEGIN IMMEDIATE` сравнивает переданный `config_version_id` с активным `resource_states.config_version_id` **до любых INSERT/UPDATE**. При несовпадении выбрасывается `StaleConfigurationResult` — результат не применяется, не попадает в `check_results`, не изменяет статус/счётчики и не создаёт outbox-событие. Даже прямой INSERT со старой версией отклоняется DB-триггером `reject_stale_check_config`.
- Изменение `active` (включая цикл `OFF -> ON`) теперь создаёт новую версию, чтобы ответ старого запроса нельзя было применить после повторного включения. Переименование `name` не меняет техническую конфигурацию и не инвалидирует сетевой запрос.
- Повторная/запаздывающая проверка той же активной версии (`checked_at <= last_checked_at`) отклоняется отдельно; timestamp **не заменяет** проверку версии.
- Отклонённый устаревший ответ рекомендуется логировать с `resource_id`, переданным и текущим `config_version_id` (без секретов); планировщик должен дождаться следующей штатной проверки уже по актуальному снимку.
- `enqueue_heartbeat_if_due()` атомарно записывает событие и обновляет `last_heartbeat_enqueued_at` внутри одной write-транзакции.
- `claim_one_event()` резервирует ожидающее событие на ограниченный срок, при этом его статус остаётся `PENDING` как указано в ТЗ; второй воркер не заберёт тот же ID до истечения аренды.
- `finish_delivery()` атомарно добавляет `delivery_attempts`, увеличивает `attempts` и выставляет `PENDING` (переотправка), `SENT` (200/202) или `FAILED` (постоянная ошибка).
- При сбое после успешного POST, но перед отметкой `SENT`, произойдёт повторная отправка после истечения lease. Поэтому доставка **at-least-once**, а получатель должен обеспечивать идемпотентность по `event_id`. Exactly-once через ненадёжный HTTP здесь не обещаем.
- Внешние запросы выполняются **вне** DB-транзакций и без удержания write-lock.

## 5. Точки разделения работы

**Никита** — `services/resources.py` (включая выдачу снимка), `services/status.py`, будущие `checks/` и планировщик, тестирование сетевых результатов и переходов.

**Артемий** — `services/events.py`, будущие HTTP sender, Mock API, FastAPI GET endpoints, Docker Compose, документация внешнего API.

**Оба** — `schema.sql`, `shared/schemas.py`, миграции, инварианты `write_transaction` и интеграционные тесты. Изменения этой части — только совместно и через Pull Request.

## 7. Ограничения и дальнейшие критерии качества

Сейчас пока не реализован полный сервис и не проведена его нагрузочная или безопасностьная проверка. В частности, перед эксплуатацией должны быть доказаны ограничения времени аренды относительно сетевого таймаута, восстановление воркера после смерти, безопасная проверка допустимости адресов (без SSRF и несанкционированного сканирования), защита токенов и логов, устойчивость к некорректным ответам API, полная интеграция и восстановление SQLite из backup. Эти требования являются задачами готовности продукта, не утверждением о готовности в этой версии.

## 8. Исправление v2.1: проверка выполняется по снимку конфигурации

**Проблема v2:** `CheckResultIn` содержал только `resource_id`, и при сохранении `apply_check_result()` использовал текущую версию из `resource_states`. Если между отправкой HTTP/TCP и получением ответа изменились таймаут или порог, старый результат мог увеличить новые счётчики и создать ошибочное `STATUS_CHANGED`. Сравнение одного `checked_at` с `last_checked_at` недостаточно: старый запрос может завершиться *позже* изменения конфигурации.

**Правильный последовательный контракт:**

```python
from db.session import read_transaction, write_transaction
from services.resources import get_active_check_snapshot
from services.status import apply_check_result, StaleConfigurationResult
from shared.schemas import CheckResultIn

# Шаг 1: до сетевого запроса; оба SELECT выполняются в одной read-транзакции.
with read_transaction(engine) as conn:
    snapshot = get_active_check_snapshot(conn, resource_id="server-001")

# Шаг 2: выполнить HTTP/TCP только с параметрами snapshot, без DB-lock.
# Выполнение сетевого запроса и формирование его значений здесь опущены.

# Шаг 3: при получении ответа передать ИСХОДНЫЙ номер версии, не перечитывая его.
result = CheckResultIn(
    resource_id=snapshot.resource_id,
    config_version_id=snapshot.config_version_id,
    checked_at=checked_at,  # aware UTC datetime завершённой проверки
    success=success,
    http_status_code=http_status_code,
    response_time_ms=response_time_ms,
    error_message=error_message,
)
try:
    with write_transaction(engine) as conn:
        outcome = apply_check_result(conn, result=result)
except StaleConfigurationResult:
    # Не пытаться применить результат к новой версии или создавать событие.
    # Зафиксировать диагностический лог, следующая штатная проверка возьмёт новый snapshot.
    pass
```

**Почему проверка атомарна:** `BEGIN IMMEDIATE` берёт write-lock до чтения актуального состояния. Если обновление конфигурации успело зафиксироваться — старая версия отвергается. Если запись результата уже началась первой — она целиком фиксируется по прежней версии до обновления конфигурации. Иными словами, возможны два согласованных порядка, но не смешанное состояние.

**Границы решения:** Отклонённые результаты не включаются в `check_results` — это история *принятых* проверок. При необходимости отдельного аудита всех отброшенных ответов следует проектировать диагностическую запись без влияния на вычисление статуса; в текущий контракт такое расширение не добавлено. Внешний JSON события и URL API ТЗ не изменены.

### Миграция с v2

Для базы, созданной `001_initial`, запускать **только** `alembic upgrade head` после обновления кода; версия `002_check_token` добавляет DB-защиту. `schema.sql` уже содержит эту защиту для тестового создания пустой БД. В версии v2.1 также исправлено имя триггера неизменяемости `outbox_events` в прежней миграции. Структура восьми предметных таблиц и исторические записи не удаляются. Обновление Pydantic-контракта требует добавить `config_version_id` во все новые объекты `CheckResultIn`.

**Регрессионные сценарии:** поздний ответ v1 после v2; `active=false -> true` во время запроса; прямой stale INSERT в SQLite; отсутствие изменений состояния/истории/outbox при отклонении; сохранение работоспособности неизменённой версии; конкурентное исполнение с управляемым порядком событий.
