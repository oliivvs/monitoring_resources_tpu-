# Ветка Никиты feature/nikita-checkers: сетевые проверки (контракт v2.1)

## Область работы

Никита разрабатывает загрузку конфигураций, безопасные HTTP/TCP-проверки, обработку статусов и планировщик. 

Код в `checks/` **не меняет** общую схему БД или внешний JSON. Он использует готовые `CheckSnapshot` и `CheckResultIn` из контракта v2.1.

## Что реализовано сейчас

- `checks/config_loader.py`: загрузка JSON/YAML, Pydantic-валидация, защита от дублированных ключей, YAML-алиасов, превышения размера и повторных `resource_id`.
- `checks/security.py`: закрытая по умолчанию политика allowlist точных хостов и портов. Запрещены запрещённые/private/link-local DNS-адреса; loopback доступен только в явном локальном тестовом режиме.
- `checks/pinned_http.py`: `httpx` + `httpcore` с DNS-pinning: подключается только к проверенному IP; исходный hostname сохраняется для Host, TLS SNI и проверки сертификата.
- `checks/probes.py`: HTTP GET (без тела ответа, без перехода по redirect) и TCP connect, DNS/таймаут/сетевые ошибки, метрики времени, правильный токен версии.
- `checks/runner.py`: `snapshot -> probe -> apply_check_result`. Сетевые операции вне транзакций; SQLite через `asyncio.to_thread`; stale-результат не меняет состояние.
- `tests/test_nikita_checks.py`: тесты на собственном локальном сервере, без сканирования внешней инфраструктуры.

### Безопасность и эксплуатация

По умолчанию `NetworkPolicy()` не разрешает **никаких** исходящих проверок. Чтобы тестировать локальный сервер, нужен явный allowlist `127.0.0.1`, явный порт и `permit_loopback_for_tests=True`. Этот флаг нельзя бездумно включать для сетевого сервера, принимающего пользовательские конфигурации.

**Важные ограничения:**
- Защита DNS pinning реализована для текущих версий `httpx`/`httpcore`; при обновлении зависимостей обязательно повторять интеграционные тесты (проверять SNI/TLS на HTTPS-сервере отдельно).
- Не используйте `verify=False`, не включайте redirect, не логируйте `target` с query и не загружайте сетевые URL без согласованного allowlist.
- Предварительное DNS-разрешение само по себе недостаточно для безопасности; *именно* PinnedHTTPTransport соединяется с разрешённым IP. Для продакшена также требуется egress firewall/контейнерные сетевые политики.
- Коды HTTP 3xx считаются ошибкой, если не входят в заданные диапазоны; редиректы не выполняются.
- Отклонение сетевой политикой (`DENIED`) не сохраняется как отказ ресурса, чтобы неправильно не перевести ресурс в `DOWN`.
- Признак `STALE` означает, что результат старой версии не сохранён после изменения конфигурации; проверка должна повториться по новому снимку в следующем плановом цикле.
- Сейчас отсутствует production scheduler и ограничение параллельности. **Не запускать массовые проверки через создание большого числа задач вручную.** Это следующая задача N08/N09.

## Проверки в Windows PowerShell

Из корня репозитория в чистом виртуальном окружении Python 3.12+:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m pytest -q
python -m scripts.local_smoke
```

Если команда `py -3.12` не находит Python, посмотрите `py -0p` и используйте установленную версию Python 3.12 или новее. Если PowerShell запрещает активацию скриптов, выполняйте `.venv\Scripts\python.exe` напрямую вместо изменения системной ExecutionPolicy.

Тесты должны выполняться без доступа к публичным ресурсам. SQLite создаётся только во временных папках pytest/smoke.

## Ограничения передачи в `main`

Перед PR: `git diff --check`, полный `python -m pytest -q`, локальный smoke, проверка изменения зависимостей, ревью второго разработчика. Ветка `main` не должна получать изменения без этих проверок.
