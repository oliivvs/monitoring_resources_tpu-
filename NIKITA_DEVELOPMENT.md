
# Мониторинг ресурсов ТПУ — модуль Никиты

Документация актуализирована для задач N03–N17 и общего контракта v2.1. Она описывает структуру кода, локальную проверку и известные ограничения.

N17 — обновление документации, а не внедрение Docker или запуск мониторинга в production. Документ не даёт разрешения проверять внутреннюю инфраструктуру ТПУ.

## 1. Ответственность модулей

| Модуль | Назначение |
| --- | --- |
| `checks/config_loader.py` | Чтение JSON/YAML и проверка конфигурации |
| `services/config_import.py` | Атомарный импорт ресурсов в SQLite |
| `services/resources.py` | Версии конфигураций и снимок параметров |
| `checks/security.py` | Сетевая политика, allowlist, DNS/IP |
| `checks/pinned_http.py` | HTTP-транспорт с DNS pinning |
| `checks/probes.py` | Одиночные HTTP/TCP-проверки |
| `checks/runner.py` | Проверка, сохранение и логирование |
| `checks/scheduler.py` | Планировщик и ограничение параллельности |
| `services/status.py` | Расчёт статусов, счётчики и история |
| `services/events.py` | Формирование событий Outbox — Артемий |
| `app/routes/resources.py` | REST API просмотра — Артемий |

Изменения считаются интегрированными в `main` только после соответствующего Pull Request.

## 2. Подготовка Windows 11

Открыть PowerShell в корне проекта:

```powershell
cd E:\monitoring_res_tpu

.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m pytest -q -W error
```

Если виртуального окружения ещё нет:

```powershell
py -3.12 -m venv .venv
```

Используем `python -m pytest`, чтобы корневая директория проекта была доступна при импорте модулей.

## 3. Локальное тестирование

```powershell
.\.venv\Scripts\python.exe -m scripts.local_smoke
.\.venv\Scripts\python.exe -m scripts.scheduler_demo
.\.venv\Scripts\python.exe -m pytest tests/test_nikita_integration_n16.py -v -W error
```

Проверки используют локальные HTTP/TCP-серверы и временные SQLite.

`scheduler_demo` проверяет переход `UNKNOWN → UP` и создание события `STATUS_CHANGED`.

Интеграционные тесты N16 проверяют HTTP, TCP, отключённые ресурсы и изменение состояний.

Обращения к реальной инфраструктуре ТПУ не выполняются.

## 4. Импорт конфигураций

Для тестирования используем отдельную SQLite.

```powershell
$env:MONITORING_DATABASE_URL = "sqlite:///n17_demo.db"

.\.venv\Scripts\python.exe -m alembic upgrade head

.\.venv\Scripts\python.exe -m scripts.import_resources --config examples/resources.yaml --database n17_demo.db
```

Повторный импорт неизменённой конфигурации не создаёт новую версию.

Изменение интервалов, таймаутов и порогов создаёт новую версию. Изменение адреса или типа проверки требует нового `resource_id`.

Импорт сам по себе не выполняет сетевых запросов.

## 5. Просмотр ресурсов через Swagger

Запуск API:

```powershell
$env:MONITORING_DATABASE_URL = "sqlite:///n17_demo.db"

.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Доступные маршруты:

- `GET /health` — состояние API.
- `GET /api/v1/resources` — список ресурсов.
- `GET /api/v1/resources/{resource_id}` — данные ресурса.
- `GET /api/v1/resources/{resource_id}/status` — текущий статус.
- `GET /api/v1/resources/{resource_id}/checks` — история проверок.

Swagger: `http://127.0.0.1:8000/docs`

Запуск FastAPI не запускает планировщик автоматически.

После импорта без проверок статус ресурса остаётся `UNKNOWN`.

## 6. Сетевые проверки и статусы

`NetworkPolicy()` по умолчанию запрещает все сетевые цели.

Разрешённые хосты и порты задаются явно. Loopback доступен только при включённом тестовом режиме.

Результаты `check_and_store()`:

- `APPLIED` — результат применён.
- `STALE` — результат устарел.
- `DENIED` — проверка запрещена сетевой политикой.
- `INACTIVE` — ресурс отключён или отсутствует.

Проверка `APPLIED` с `success=False` означает обнаруженную недоступность ресурса, а не ошибку приложения.

Пороги по умолчанию:

- `up_after=2` — два успешных результата подряд.
- `down_after=3` — три неуспешных результата подряд.

Результат проверки, статус и событие сохраняются одной транзакцией SQLite.

Отправкой событий занимается отдельный модуль Артемия.

## 7. Логирование и безопасность

Логирование N15 различает:

- `APPLIED`
- `STALE`
- `DENIED`
- `INACTIVE`
- `ERROR`
- `CANCELLED`

Ошибки разделяются по этапам `snapshot`, `probe` и `persist`.

В новые логи не включаются URL с query-параметрами, токены, содержимое ответов и тексты исключений.

Использование реальных адресов ТПУ возможно только после согласования сетевых целей и разрешений.

## 8. Известные ограничения

1. `scripts/scheduler_demo.py` — демонстрация, а не рабочая служба. Отдельная команда для непрерывного запуска планировщика пока не представлена.

2. FastAPI не запускает мониторинг автоматически.

3. `scripts/run_sender.py` использует `loop.add_signal_handler`, который не поддерживается стандартным циклом событий Python на Windows. Требуется совместная доработка с Артемием.

4. Отмена задачи во время `asyncio.to_thread` не гарантирует остановку уже начатой SQLite-операции.

5. Docker Compose, непрерывный запуск всех компонентов, восстановление SQLite и производственная эксплуатация пока не подтверждены.

6. Для эксплуатации необходимы дополнительные проверки безопасности сетевого доступа, HTTPS/TLS и резервного копирования.

## 9. Docker и совместная интеграция

### Артемий — A15

Ответственный за Docker Compose и постоянное хранение SQLite.

Задачи:

- Создать Dockerfile и Compose-конфигурацию.
- Настроить том SQLite.
- Подготовить переменные окружения.
- Организовать запуск FastAPI.
- Организовать запуск Mock API.
- Организовать запуск отправителя событий.

### Никита — модуль мониторинга

Отвечает за включение мониторинга в общее окружение:

- Запуск планировщика как долгоживущей службы.
- Подключение к общей SQLite.
- Настройку разрешённых HTTP/TCP-целей.
- Корректное сохранение статусов и событий.
- Логирование и завершение проверок.

Локальная демонстрация `scheduler_demo.py` не заменяет рабочий запуск планировщика.

### Совместные задачи

- C04 — расчёт статуса и запись события в одной транзакции.
- C05 — HEARTBEAT в общем цикле.
- C06 — сквозной сценарий `UP → DOWN → UP`.
- C07 — сбои, HTTP 500, повторы, дубли и перезапуск.
- C08 — взаимное ревью и объединение PR.
- C09 — финальная демонстрация и устранение замечаний.

### Критерии готовности интеграции

1. Контейнеры успешно запускаются.
2. Ресурсы импортируются в SQLite.
3. API отображает конфигурации и статусы.
4. Планировщик выполняет разрешённые проверки.
5. История и переходы сохраняются в SQLite.
6. События создаются в Outbox.
7. Отправитель доставляет события в Mock API.
8. Повторное событие не создаёт дубль у получателя.
9. Перезапуск не приводит к потере SQLite и очереди.
