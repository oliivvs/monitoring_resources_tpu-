# ТПУ Monitoring API — интеграционный контракт v1

**Версия:** 1.0-draft  
**Дата:** 08.11.2026  
**Статус:** проект для согласования между командами  
**Репозиторий:** https://github.com/oliivvs/monitoring_resources_tpu-

## 1. Назначение интеграции

Сервис «Мониторинг ресурсов ТПУ» выполняет периодические проверки доступности HTTP/HTTPS- и TCP-ресурсов, определяет их текущее состояние и предоставляет результаты внешним информационным системам.

Взаимодействие с внешним проектом осуществляется двумя способами:

- **Push:** мониторинг самостоятельно отправляет HTTP POST при изменении статуса ресурса и при формировании HEARTBEAT.
- **Pull:** внешняя система запрашивает актуальные статусы через REST API мониторинга.

Использование Push и Pull совместно необходимо для своевременного получения изменений, первоначальной синхронизации и восстановления данных после сбоев.

Один `resource_id` соответствует одной проверяемой службе и одному типу проверки. Несколько служб одного физического сервера могут иметь разные `resource_id`.

## 2. Статусы ресурсов

| Статус | Значение |
|---|---|
| `UNKNOWN` | Доступность ресурса ещё не подтверждена |
| `UP` | Ресурс признан доступным |
| `DOWN` | Ресурс признан недоступным |

Правила определения статуса по умолчанию:

- После **2 последовательных успешных проверок** устанавливается `UP`.
- После **3 последовательных неудачных проверок** устанавливается `DOWN`.
- Пороговые значения могут изменяться в конфигурации мониторинга.

Единичная неудачная проверка не означает немедленного перехода в `DOWN`.

Статус относится к конкретной проверяемой службе. Например, успешная TCP-проверка порта не гарантирует корректную работу всех функций приложения на сервере.

## 3. Push API — передача событий

### 3.1. Точка приёма

Предлагаемый интерфейс принимающей системы:

**POST `/api/v1/status/events`**

Точный базовый URL предоставляется командой получателя.

Заголовки запроса:

    Authorization: Bearer <EVENT_TOKEN>
    Content-Type: application/json

На стороне мониторинга подключение настраивается через:

    MONITORING_EVENT_POST_URL
    MONITORING_EVENT_TOKEN

### 3.2. Формат события

```json
{
  "event_id": "37253074-ee80-437b-9aa1-5344fd057956",
  "event_type": "STATUS_CHANGED",
  "resource_id": "test-server",
  "resource_name": "Тестовый HTTP-сервер",
  "status": "DOWN",
  "check_type": "HTTP",
  "checked_at": "2026-11-08T14:12:11.136294Z",
  "response_time_ms": 31.644,
  "error": "Ошибка сети: ConnectionError"
}
```

### 3.3. Поля события

| Поле | Тип | Назначение |
|---|---|---|
| `event_id` | UUID | Уникальный идентификатор события |
| `event_type` | string | `STATUS_CHANGED` или `HEARTBEAT` |
| `resource_id` | string | Постоянный идентификатор проверяемой службы |
| `resource_name` | string | Название ресурса |
| `status` | string | `UNKNOWN`, `UP` или `DOWN` |
| `check_type` | string | `HTTP` или `TCP` |
| `checked_at` | datetime | Время последней проверки, UTC |
| `response_time_ms` | number/null | Время проверки в миллисекундах |
| `error` | string/null | Информация об ошибке проверки |

Все поля присутствуют в JSON. Значения `response_time_ms` и `error` могут быть `null`.

Время передаётся в ISO 8601 с UTC-суффиксом `Z`.

### 3.4. STATUS_CHANGED

Событие `STATUS_CHANGED` создаётся при первом подтверждённом статусе и при каждом последующем изменении состояния.

Примеры переходов:

    UNKNOWN → UP
    UP → DOWN
    DOWN → UP

Если статус не меняется, повторное событие `STATUS_CHANGED` не создаётся.

### 3.5. HEARTBEAT

**Статус реализации: функция формирования существует, автоматический запуск ещё требуется подключить.**

Периодическое событие `HEARTBEAT` подтверждает работу механизма мониторинга и передачи данных даже в отсутствие изменений статусов.

Предлагаемый интервал по умолчанию — **300 секунд**. Он может настраиваться для каждого ресурса.

Формат JSON остаётся тем же, но:

    "event_type": "HEARTBEAT"

Поле `status` содержит текущее состояние ресурса, включая `DOWN`.

Поле `checked_at` относится к последней проверке, а не обязательно к моменту создания HEARTBEAT.

Получение HEARTBEAT не означает, что проверяемый сервер доступен. Оно означает, что мониторинг передал информацию о его состоянии.

Получателю рекомендуется отдельно учитывать:

- `checked_at` — свежесть самой проверки;
- локальное время получения события — свежесть связи с мониторингом.

Отсутствие новых событий дольше согласованного интервала должно приводить к отметке **«данные устарели»**, а не к автоматической замене статуса на `DOWN`.

## 4. Подтверждение доставки и обработка ошибок

При успешном получении нового события принимающая система отвечает HTTP `202 Accepted`.

Пример:

```json
{
  "event_id": "37253074-ee80-437b-9aa1-5344fd057956",
  "result": "accepted"
}
```

При повторном получении идентичного события с тем же `event_id` получатель возвращает HTTP `200 OK`:

```json
{
  "event_id": "37253074-ee80-437b-9aa1-5344fd057956",
  "result": "duplicate"
}
```

Оба HTTP-кода считаются успешной доставкой.

| Результат | Поведение отправителя |
|---|---|
| `200`, `202` | Событие помечается как `SENT` |
| `429` | Повторная попытка с учётом `Retry-After` |
| `5xx` | Повторная попытка с задержкой |
| Сетевая ошибка / таймаут | Повторная попытка |
| Остальные `4xx` | Событие помечается как `FAILED` |

При `401` необходимо исправить авторизацию. Автоматическая повторная отправка такого события без вмешательства не предусмотрена.

**Гарантия доставки — at-least-once, а не exactly-once.**

Событие может поступить повторно, например если получатель сохранил его, но подтверждение не дошло до отправителя.

Поэтому получатель обязан сохранять обработанные `event_id` в постоянном хранилище и обеспечивать идемпотентность.

Если один `event_id` приходит повторно с отличающимся содержимым, получатель должен отклонить запрос, например с HTTP `409 Conflict`.

## 5. Pull API — получение данных

### 5.1. Существующие методы

На стороне мониторинга реализованы:

| Метод | URL | Описание |
|---|---|---|
| GET | `/health` | Доступность API мониторинга |
| GET | `/api/v1/resources` | Список ресурсов |
| GET | `/api/v1/resources/{resource_id}` | Информация о ресурсе |
| GET | `/api/v1/resources/{resource_id}/status` | Текущий статус |
| GET | `/api/v1/resources/{resource_id}/checks` | История проверок |

Методы списка ресурсов и истории поддерживают параметры `limit` и `offset`.

Пример существующего ответа:

**GET `/api/v1/resources/test-server/status`**

```json
{
  "resource_id": "test-server",
  "status": "UP",
  "checked_at": "2026-11-08T14:12:43.862693Z",
  "error": null
}
```

В существующей реализации методы GET пока не имеют отдельной Bearer-авторизации. Перед предоставлением доступа другому проекту её необходимо реализовать.

### 5.2. Планируемый GET /api/v1/statuses

**Статус: предлагаемый интерфейс v1, требуется реализация.**

Назначение: получить текущие состояния всех доступных для интеграции ресурсов без запроса каждого ресурса отдельно.

Запрос:

    GET /api/v1/statuses?limit=50&offset=0
    Authorization: Bearer <READ_TOKEN>

Предлагаемый формат ответа:

```json
{
  "items": [
    {
      "resource_id": "test-server",
      "resource_name": "Тестовый HTTP-сервер",
      "check_type": "HTTP",
      "status": "UP",
      "active": true,
      "checked_at": "2026-11-08T14:12:43.862693Z",
      "status_changed_at": "2026-11-08T14:12:43.862693Z",
      "error": null
    }
  ],
  "limit": 50,
  "offset": 0,
  "has_more": false
}
```

Это **проект ответа**, а не действующий формат существующего метода.

Поля `checked_at` и `status_changed_at` допускают `null` для нового ресурса без проверок.

`active=false` означает, что ресурс исключён из текущих проверок. Последний сохранённый статус такого ресурса не следует отображать как подтверждение актуальной доступности.

Ресурсы возвращаются в стабильном порядке по `resource_id`.

Параметр `has_more` сообщает о наличии следующей страницы. Последовательная загрузка страниц с `offset` не гарантирует идеально согласованный снимок при одновременном изменении списка ресурсов; поэтому после первичной загрузки необходима сверка, а для более строгих требований в дальнейшем можно добавить серверные snapshot/cursor.

Внешний API статусов не должен раскрывать внутренние сетевые адреса или чувствительные параметры конфигурации.

### 5.3. Ошибки GET API

Предлагаемые коды:

| Код | Значение |
|---|---|
| `200` | Запрос выполнен |
| `401` | Токен отсутствует или неверный |
| `403` | Недостаточно прав |
| `404` | Запрошенный ресурс не найден |
| `422` | Некорректные параметры |
| `5xx` | Временная ошибка сервера |

## 6. Первоначальная синхронизация

При первом подключении получателю необходимо получить актуальные состояния ресурсов, даже если изменения статуса произошли до его запуска.

Предлагаемый порядок:

1. Получатель запускает обработчик POST-событий и начинает принимать или буферизовать входящие сообщения.
2. Получатель запрашивает все страницы `GET /api/v1/statuses`.
3. Каждый ресурс сохраняется по ключу `resource_id`.
4. События, поступившие во время синхронизации, сопоставляются с полученным снимком.
5. Для обновления статуса используется более новое значение `checked_at`; более старое событие не должно перезаписывать новое состояние.
6. После первоначальной загрузки выполняется повторная сверка GET, затем система переходит к обычной работе.

Возможность параллельного поступления POST и GET должна учитываться при реализации получателя.

Для одного ресурса необходимо различать три времени:

- время проверки `checked_at`;
- время изменения статуса `status_changed_at`, если оно получено через GET;
- локальное время приёма события.

Повторные события с известным `event_id` не создают новые записи об изменениях.

Для одинаковых временных меток нельзя полагаться только на порядок прихода HTTP-запросов. HEARTBEAT не должен отменять уже подтверждённое изменение статуса.

## 7. Периодическая сверка и восстановление после сбоя

Даже при работающем Push-канале получатель периодически запрашивает GET-данные.

**Предлагаемый интервал сверки: 5 минут.** Окончательный интервал согласовывается командами.

Повторная синхронизация выполняется также после перезапуска получателя или длительного отключения связи.

Сверка должна:

- добавлять ранее неизвестные ресурсы;
- обновлять более старые состояния;
- учитывать признак `active`;
- не создавать дубли ресурса;
- не удалять весь локальный список при временной ошибке GET.

Если GET временно недоступен, получатель сохраняет последнее известное состояние и отдельно отмечает его свежесть.

## 8. Безопасность

Для постоянной интеграции требуются следующие правила.

**Push:**
- Использование HTTPS.
- Bearer Token в заголовке `Authorization`.
- Хранение токена в переменных окружения или секретном хранилище.
- Запрет записи токена в логи.

**Pull:**
- Отдельный токен чтения `READ_TOKEN` либо эквивалентный согласованный механизм авторизации.
- HTTPS.
- Ограничение доступа к данным разрешённых ресурсов.
- Отсутствие чувствительных конфигурационных данных в ответах внешнего API.

Секреты не включаются в Git и передаваемую документацию.

Конкретные базовые URL, токены, доступность сетей и требования к TLS согласовываются перед совместным развёртыванием.

| Формирование HEARTBEAT | Команда мониторинга |

## 10. Критерии приёмки интеграции

Интеграция считается готовой к совместному испытанию, когда выполнены следующие условия:

- [ ] Получатель успешно принимает `STATUS_CHANGED` со статусами `UP` и `DOWN`.
- [ ] Изменения обнаруживаются мониторингом согласно настроенным порогам.
- [ ] Повторный `event_id` не создаёт дубликат.
- [ ] Получатель принимает `HEARTBEAT` и не трактует его как смену статуса.
- [ ] GET API возвращает актуальный перечень статусов.
- [ ] После первого подключения получатель загружает существующие состояния.
- [ ] Старые POST-события не перезаписывают более новые данные из GET.
- [ ] При временной недоступности получателя события остаются в очереди.
- [ ] После восстановления получателя повторная отправка завершается успешно.
- [ ] После перезапуска обе системы восстанавливают необходимые данные.
- [ ] Проверены авторизация, некорректные токены, ошибки `429` и `5xx`.
- [ ] Проверена совместная работа в выбранной среде развёртывания.

- Сохранение истории проверок и событий в SQLite.
- Отправка событий HTTP POST с Bearer Token.
- Успешное принятие событий Mock API.

## 12. Вопросы для окончательного согласования

До присвоения контракту статуса `v1.0 approved` команды должны утвердить:

1. Точный URL приёма POST и правила выдачи токена.
2. Предлагаемый формат `GET /api/v1/statuses` и его пагинацию.
3. Способ авторизации GET и перечень разрешённых ресурсов.
4. Интервал HEARTBEAT и критерии устаревания данных.
5. Правила порядка обработки одновременно поступающих GET-снимков и POST-событий.
6. Адреса тестовой и постоянной сред, сетевые доступы.
7. Требования к хранению истории и срокам восстановления после сбоя.

После утверждения этих пунктов структура JSON и семантика методов фиксируются как контракт v1. Несовместимые изменения должны выпускаться в новой версии API.
